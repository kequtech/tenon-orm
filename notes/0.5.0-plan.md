# Tenon 0.5.0 plan

Status: implemented for Tenon 0.5.0, pgclear 0.3.5 and pgclear-jobs 0.2.1. The scope was approved
on 2026-11-02, including freedom to improve Tenon's API without compatibility constraints, patch
versions for the supporting packages, and a request to keep implementations simple. Publication
and pushing remain explicitly out of scope. The original rationale and deferred scope are retained
below; the implementation/validation record at the end describes what shipped in this candidate.

## Direction

Make Tenon easier to learn and use in an existing application. Keep explicit SQL, ordinary
functions, application-owned migrations, and a thin Jobs integration. The documentation overhaul
is a release requirement in its own right. A new queue subsystem is not the purpose of 0.5.0.

The consumer reports establish useful integrations and specific friction, rather than a reason to
change the architecture. All three report no reproducible library correctness blocker in the paths
they exercised. Their test totals are consumer-reported evidence, not checks rerun for this plan;
they do not establish production capacity or behavior under every failure mode.

Tenon remains the primary entry point. The repositories keep separate source, dependencies,
lockfiles, tests, and releases. Changes cross their boundaries through public package APIs and
packed artifacts, with no shared source directory, cross-repository source imports, or new workspace.

| Owner        | Responsibility in this release                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------ |
| tenon-orm    | Documentation, source checking, ORM typing/guards, thin Jobs forwarding and re-exports           |
| pgclear-jobs | Queue record APIs, scheduling, worker lifecycle and storage compatibility                        |
| pgclear      | Original driver errors and evidence about individual operation outcomes                          |
| Application  | Process supervision, business identity/results, authorization and external-effect reconciliation |

## Feedback decisions

These decisions define the accepted scope; deferred requests remain deferred.

| Request                                      | Decision                                         | General value and limit                                                                                                  |
| -------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Full Tenon documentation overhaul            | Required                                         | A coherent route from setup to daily work, with fewer guides and less repeated explanation                               |
| Bulk job lookup                              | Include                                          | Removes N+1 queue reads in any status projection; retain unknown payloads for heterogeneous IDs                          |
| Scheduled keyed requests                     | Include                                          | Scheduled, startup and manual triggers can use the same durable execution key across processes                           |
| Error-tree inspection                        | Include a small pgclear helper                   | Removes repeated traversal while preserving original errors and their individual evidence                                |
| Readiness/lifetime handle                    | Include a small optional Jobs API                | Repeated framework-host bookkeeping has a common shape; retain `run` and application supervision                         |
| Finite identifier helper parameters          | Include a bounded checker extension              | Ordinary finite name choices should be checkable without a general TypeScript interpreter                                |
| Minimum grants and storage-upgrade guidance  | Required                                         | Permissions and app-owned migration changes must be reproducible rather than inferred                                    |
| Next.js hosting recipe                       | Include in documentation                         | Explain framework-owned exit behavior and show a tested process-hosting pattern                                          |
| Cooperative cancellation of running jobs     | Defer implementation; specify its contract first | Useful capacity control, but requires a separate ownership/race design; existing business fences still matter            |
| Pagination iterator                          | Defer                                            | Keep cursor `find`, document a complete loop and test beyond 100 records; bulk lookup addresses the separate N+1 problem |
| Optional storage namespaces                  | Defer                                            | Current isolated-database testing works; changing every storage path is disproportionate to the demonstrated need        |
| Published Jobs changelog marked “Unreleased” | Fix during release preparation                   | Correct release metadata without inventing a publication date or changing existing migration SQL                         |

Do not add automatic migrations, transaction replay, durable application results, a process manager,
a framework adapter, or an application repair framework. Producer contracts, worker bindings,
observation hooks and original-error escalation already address the earlier requests in those areas.

## Documentation overhaul

The current `docs/` has 15 Markdown files, approximately 3,000 lines before the README/changelog.
The main problem is divided ownership of explanations, not just length:

- First-use, agent and reference pages repeat query, configuration, transaction and validation advice.
- Queries and writes are separate even though readers need their result modes, encodings and guards together.
- Runtime setup is spread across configuration, connections and reference pages; migration adoption
  and schema snapshots add more routes for maintaining the same database.
- Jobs requires its guide, a workflow guide and the supporting package reference for common questions.
- Some advice disagrees: the end of `mutations.md` says checking needs required selected fields,
  while `query-checking.md` describes the implemented finite optional-field support.
- The schema-snapshot guide is linked from prose but missing from the README's guide table.

Replace the guide structure rather than concatenate the existing files. Keep seven consumer pages
under `docs/`, with the README as the index. No new documentation framework or documentation site
is needed. The names below are proposed destinations, not current links.

| Destination          | Reader's task                                                                    | Material to consolidate                                                                  |
| -------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `getting-started.md` | Connect, migrate a small table, query it, then find the next task                | `human-guide.md`; the existing-project workflow from `agent-guide.md`                    |
| `queries.md`         | Read/write data, reuse queries, compose SQL and control transactions             | `sql.md`, `mutations.md`; transaction and guard explanations currently in `reference.md` |
| `database.md`        | Configure, host and evolve an application database                               | `configuration.md`, `connections.md`, `migrations.md`, `adoption-guide.md`               |
| `types.md`           | Generate storage types and choose input/output representations                   | `schema-types.md`                                                                        |
| `checking.md`        | Choose and use freshness checks, source checks, Describe and schema fingerprints | `query-checking.md`, `query-inspection.md`, `schema-inspection.md`                       |
| `jobs.md`            | Install storage, produce work, run workers and design reliable workflows         | `jobs.md`, `job-workflows.md`; hosting/grants additions                                  |
| `reference.md`       | Look up signatures, options, errors and CLI syntax                               | A rewritten lookup reference linking to each concept's owning guide                      |

The README should show one complete small query and a short task index. Getting started should
have one uninterrupted path using one example schema/configuration and consistent import/run
conventions. Give existing applications a short entry point that preserves their schema, migration
runner and package manager. Agents and people use the same guides; agent-specific cautions do not
need a second tutorial.

Each concept has one detailed explanation. The reference owns exact signatures, option/default
tables and command syntax; guides own workflows and examples. A local contents list makes a longer
page searchable. Put the common path first and advanced variants later. Moving every paragraph into
seven longer files would not satisfy this overhaul.

Preserve useful detail: values/codecs, omitted versus null fields, transaction boundaries and
guards, borrowed pools/listeners, baseline adoption, schema-fingerprint limits, checker uncertainty,
Jobs retries/keys/retention, uncertain commits and external effects. Reduce repeated cautions and
examples, not these contracts. Common Tenon/Jobs tasks must be understandable from installed docs;
version-specific upstream references are supplemental.

Update internal links, anchors, maintainer instructions and package-consumer file expectations
together. Document the old-to-new page mapping in the 0.5.0 changelog. Keep prior-version docs in
their Git tags rather than shipping eight retired guides as forwarding stubs.

Documentation acceptance:

- A reader can complete setup, a reusable query, a guarded write and a database test without
  reconstructing an example across multiple pages.
- A reader can find one authoritative answer for value mappings, configuration defaults,
  transaction failures and each validation tool's limits.
- Freshness, TypeScript compilation, SQL checking, Describe and execution tests are explicitly
  distinguished; checker success never implies proven nullability or runtime validation.
- Jobs includes complete cursor pagination, durable application results, independent transaction
  failures, pool capacity, grants and framework hosting without adding application orchestration APIs.
- Important examples compile against the packed public API and observable workflows run against
  disposable test storage. Relative file links and section anchors resolve in the packed artifact.
  Extend existing checks where necessary; do not test prose wording.

## Implementation contracts

### Bulk lookup — pgclear-jobs, forwarded by Tenon

Add `getMany(ids)` alongside `get`. Proposed result: found records once each, in first-requested
order; missing IDs are omitted. Empty input returns an empty array without SQL, malformed IDs reject
before SQL, and a bounded batch limit is documented. Mixed-name lookups retain unknown payloads,
as `get` does; a caller-supplied generic must not assert unverified payload types.

Use one database statement for a nonempty batch. Verify duplicate/missing IDs, ordering, limits,
transaction visibility/rollback and empty input. Tenon's root/transaction facades must retain
closed/expired-scope checks even for empty input. No storage change should be necessary.

### Scheduled keyed requests — pgclear-jobs

Give a schedule an explicit request key separate from its existing identity `key`; `requestKey`
is a candidate option name. With no request key, preserve ordinary occurrence behavior. With one,
each due tick performs the same durable request/coalescing operation as manual submissions,
atomically with advancing that schedule's cursor.

Preserve a started head's saved policy, retries and backoff, and at most one coalesced successor.
Proposed timing rule: a scheduled tick acts like `request` without timing overrides, so it does not
postpone an existing pending job or successor. A newly created request is eligible immediately.
Payload replacement follows existing request semantics; sticky force intent stays application-owned.

Resolve occurrence metadata before implementation: multiple schedules and manual producers may
coalesce into one job, so a job cannot pretend to belong exclusively to every contributing schedule.
Define what `lastJobId`, `scheduledFor`, unscheduling and manual retry mean in this mode. Do not
apply the current one-outstanding-job-per-schedule index blindly to a keyed head and successor.

Test multiple runners, two schedules sharing a request key, startup/manual overlap, retries,
completion races, missed ticks, schedule edits, unscheduling and rollback. These are durable queue
semantics owned entirely by Jobs, not a dispatcher implemented in Tenon.

Persisting request keys requires a storage compatibility change unless the design demonstrates a
different durable representation. Plan an explicit upgrade artifact and migration tests below;
do not disguise it as an API-only addition.

### Error inspection — pgclear, directly re-exported by Tenon

Expose one small traversal helper for DriverErrors reachable through `cause` and AggregateError
members. Finalize its name and return shape in pgclear. Preserve object identity and code/outcome
fields; deduplicate shared nodes and handle cycles and unknown/non-Error thrown values. Traversal
must not wrap, replace, serialize or log the original exception.

Return evidence, not a blanket retryable/committed flag. `outcome: 'confirmed'` for an individual
operation does not prove its surrounding transaction committed. Presence of `PGCLEAR_COMMIT_UNKNOWN`
must remain distinguishable from an ordinary unknown statement outcome; absence proves neither
rollback nor commit. Application reconciliation and escalation policy remain explicit.

Test nested causes, aggregates, duplicates, cycles, cleanup failures and original identities.
Keep transport fault tests establishing outcome evidence; the helper itself is a pure unit-tested
operation. Jobs can consume it if useful, but should not translate its errors into new classes.

### Readiness/lifetime handle — pgclear-jobs, forwarded by Tenon

Add an optional start operation returning `{ ready, done }`, with the application's existing signal.
Keep `run` as the supported lifetime-promise API. Use one runner implementation and readiness
milestone: storage validation and successful completion of any existing `onReady` callback, before
dispatch. Readiness is not continuous health, listener readiness or proof of processing progress.

Specify startup rejection, callback rejection, shutdown before readiness, pre-aborted signals and
late runner failure. Neither promise may remain pending after startup is cancelled; preserve
original errors and install rejection observation immediately. The handle owns no process signals,
restart policy or database close. Tenon forwards it without recreating lifecycle bookkeeping.

Use real startup/shutdown tests, including startup hooks that return after readiness while still
observing `done`. A Next.js recipe should run the framework and worker as supervised child
processes so framework-owned process exit cannot bypass worker cleanup. Verify child failure,
SIGINT/SIGTERM and ordered pool close; use an isolated framework fixture rather than adding a
framework runtime dependency to the libraries.

### Finite identifier parameters — Tenon

The checker already recovers const/conditional identifiers and small fragment-only factories.
Start by supporting identifier arguments whose effective TypeScript type is a finite string-literal
union, including a helper parameter. Describe every possible quoted name under the existing
16-variant and 32-reference limits. Recover type information without executing application helpers.

Independently expanding table and column unions is insufficient when only certain pairs are valid.
Preserve correlations only where the source/type relationship establishes them; otherwise retain
an explicit unchecked diagnostic rather than claim a contradiction from an invented pairing.
Broad strings, mutable unknown choices, casts that erase evidence, recursion and excessive variants
must not silently become checked. This is bounded recovery, not general function-body analysis.

Prototype this before committing to broader helper support. Cover both positive independent choices
and negative/unresolved correlated choices, imported aliases, invalid identifiers, budget overflow
and a real mismatch in one valid variant. Use ordinary domain-neutral tables. The two image-write
exceptions are examples of the gap, not a requirement to special-case that application's closure.
If its exact correlation cannot be recovered within this scope, keep the exception and document why.

### Grants and storage compatibility — pgclear-jobs, explained through Tenon

Provide a tested owner/runtime-role recipe: schema usage, schema-version reads, table privileges,
and required function execution. Revoke PUBLIC execution explicitly and prove the runtime role
can submit, request, schedule, execute, retry and prune without owning storage or running DDL.
Distinguish a producer-only role where practical. No grants example should imply isolation between
applications merely because their job names differ.

For any new storage version, ship concrete reviewable upgrade SQL and compatibility notes with the
Jobs package. Keep saved application migrations immutable and new installation SQL separate from
upgrade SQL. Tenon's setup command must not automatically apply upgrades or rewrite the old pair.
Test fresh installation versus upgrade from version 1 with queued/running/retrying/scheduled data,
and state worker/producers' required stop/upgrade/restart order. Reject incompatible storage clearly;
do not promise mixed-version operation unless it is tested. Explain reversal/data-loss limits.

## Deferred work

Active cancellation deserves a separate contract covering who can request it, durable request versus
completed cancellation, cross-process signal propagation, transaction rollback, attempt history,
head/successor promotion, lease recovery and cancellation/completion races. Notifications can reduce
latency but cannot be the only durable mechanism. Nontransactional external effects remain
cooperative, and an uncooperative JavaScript handler must not free a concurrency slot while it is
still running. Preserve today's pending-only `cancel` behavior until a deliberate API change is ready.
Do not make implementation a hidden 0.5.0 release gate.

Reconsider an iterator only after the documented cursor loop and bulk lookup leave meaningful
repeated code. Reconsider namespaces when a consumer needs independent queue installations in one
physical database beyond the existing fixed-schema/test-database arrangement. Neither requires a
configuration flag now.

## Delivery order and release checks

1. **Documentation foundation.** Rewrite the seven-guide structure against today's API, fix
   contradictions and update links/package expectations. New APIs land with their own examples later.
2. **Small independent APIs.** Implement/test error inspection in pgclear and bulk lookup in Jobs,
   then integrate their public artifacts in Tenon. Complete the optional lifecycle handle and hosting
   recipe without changing pool ownership.
3. **Scheduling and storage.** Finalize keyed-schedule metadata/timing, then implement it with the
   explicit storage upgrade, grants tests and ordinary-schedule regressions. This is the largest
   accepted queue change; complete its contract before coding.
4. **Bounded checker work.** Prototype finite parameters, keep conservative unsupported diagnostics,
   and update the checking guide to the behavior actually delivered.
5. **Release candidate.** Reconcile documentation with final APIs; finish 0.4.11-to-0.5.0 upgrade
   notes, supporting-package changelogs and package versions. Publish only when explicitly requested.

For each implementation, run focused behavioral/type checks, then the affected repository's normal
checks. Before release, run all affected repositories' complete checks, PostgreSQL 16/18 coverage
and Tenon's TypeScript 6/7 packed-consumer checks. Compile/run representative guide examples and
check packed links including anchors. Source tests alone do not validate the installed dependency graph.

Use the existing local-tarball candidate mechanism in `CONTRIBUTING.md` for cross-package validation.
Verify one actual pgclear module/error identity from the consumer, Tenon and Jobs entry points.
Keep candidate paths out of committed manifests/lockfiles. Supporting packages keep their own
versions and compatibility ranges; no synchronized 0.5.0 version is implied. Publish required
supporting packages first, then validate Tenon against registry dependencies without overrides.

Recheck the reported workflow shapes with isolated consumers: status projection over more than
100 records, shared-key scheduled/manual maintenance, framework startup/failure/shutdown and finite
identifier checks. These are acceptance examples; do not expand scope into rewriting the applications.
Existing pgclear-jobs documentation edits are unrelated pre-existing work and must be preserved.

## Implementation and validation record

- Replaced the 15 consumer guides with the seven destinations above, roughly halving their total
  line count. README navigation, historical changelog links, package expectations and heading-anchor
  checks now use that structure. Maintainer notes stay outside the package.
- Added `getMany`, `startJobs` / `db.jobs.start`, finite immutable identifier parameters and the
  directly re-exported `findDriverErrors`. Runtime algorithms remain in their owning packages.
- Added schedule `requestKey`. Shared jobs have no exclusive schedule ID/date; each schedule records
  the shared job in `lastJobId`. Ticks preserve existing due times, saved policy and retry backoff.
- Storage version 2 adds only `schedules.request_key`. The explicit version-1 upgrade preserves
  outstanding jobs/attempts/schedules; downgrade refuses to discard configured request keys.
- Added the runtime grants SQL and a real disposable Next 16.4.2 fixture. Its signal tests established
  that Next exits with code 143 after handling SIGTERM; the example treats that specific shutdown
  as expected while still supervising worker and framework failures.
- PostgreSQL 16 and 18: Tenon's full checks passed (311 tests per run, including packed TypeScript
  6/7 consumers, installed documentation links/anchors and actual Next hosting). Jobs passed its
  full checks (23 unit/package tests and 174 database tests per major). Pgclear passed its full
  PostgreSQL 16 checks (155 unit/package tests and 120 integration tests, with one native-Temporal
  skip in each group on Node 24.4.1), and all 120 PostgreSQL 18 integration tests with one native-
  Temporal skip. Separate packed-copy traversal checks preserve error object identity.
- Tests used existing PostgreSQL 16 test configuration and disposable Jobs/PostgreSQL 18 storage;
  consumer application repositories, deployment state and configured queue contents were preserved.
- Supporting patches remain unpublished. Tenon's dependency ranges require those patch versions;
  their lock entries have no fabricated registry URL/integrity. Cross-package checks used packed
  artifacts through the existing candidate mechanism. Publishing the patches, refreshing authentic
  registry lock metadata and running clean registry-only checks remain explicit future release steps.
- Existing edits in Jobs' implementation-plan, integration guide and todo file were preserved and
  excluded from this work's commit.
